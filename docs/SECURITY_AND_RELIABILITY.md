# 보안·안정성 개선 단계

작업 브랜치: `codex/security-and-reliability`

## 1. 접근 통제와 출력 보안

- 공개 여부를 `published !== false && isPrivate !== true`로 통일했습니다. 필드가 없는 예전 공개 글은 유지합니다.
- 상세 API는 비공개 글을 관리자에게만 반환합니다. 서버 렌더링/SEO 조회는 항상 공개 글만 반환합니다.
- 관리자 데이터 API는 공용 캐시에 저장하지 않습니다. 로그아웃 시 클라이언트에서도 비공개 목록/본문을 지웁니다.
- 작성 미리보기와 상세 화면을 ReactMarkdown → raw HTML 파싱 → 허용 목록 정화 → heading ID 생성 순서로 통일했습니다. 표/동영상은 유지하고 script, 이벤트 속성, 실행형 URL은 제거합니다.
- JSON-LD의 `<`를 이스케이프합니다. 표 입력은 HTML로 해석되지 않도록 문자로 삽입합니다.
- 서버 키의 next.config 주입을 제거하고 server-only 경계를 추가했습니다.
- 파일은 실제 바이트/MIME, Base64, 요청 스트림 크기를 검사합니다. 서버 UUID 파일명으로 덮어쓰기를 막습니다. 호스팅 요청 한도를 고려해 파일당 3MB로 제한했습니다.
- 포트폴리오 URL은 http/https만 허용합니다.

## 2. 데이터와 인증 복원

- 수정 API는 허용된 편집 필드만 저장합니다. 작성일·작성자·통계·추천 여부는 수정 요청으로 변경할 수 없습니다.
- 생성 시 작성자·작성일·통계는 서버에서 설정합니다. Firebase 클라이언트 Timestamp sentinel을 JSON으로 전송하지 않습니다.
- 기존 첨부 메타데이터를 유지하며 삭제된 본문 파일만 목록에서 제외합니다.
- 인증 복원과 서버 관리자 확인이 끝날 때까지 작성 페이지 리다이렉트를 대기합니다. 관리자 이메일은 인증된 이메일이어야 합니다.
- 글·포트폴리오 변경 시 관련 페이지/사이트맵을 무효화합니다.

## 3. 조회, 구조, 의존성

- 목록 Firestore 조회에 필드 projection을 적용해 본문/첨부파일을 다운로드하지 않습니다. (4단계에서 DB 페이지네이션까지 적용)
- 최신 5개를 포함한 전체 목록에 카테고리 필터를 적용합니다. 화면의 더 보기는 4단계에서 실제 DB 다음 페이지 조회로 교체했습니다.
- 조회 오류와 실제 빈 목록을 구분하고 재시도를 제공합니다.
- 날짜·정렬 유틸을 공유하고 한국 시간대의 중복 보정을 제거했습니다.
- 표 편집기를 독립 컴포넌트로 분리해 입력 시 재마운트/포커스 손실을 방지합니다.
- AWS SDK v3와 모듈형 Firebase Admin으로 변경했습니다. 미사용 marked/headlessui를 제거했습니다.
- Amplify 공식 지원 범위를 고려해 Next.js 15.5.29를 사용합니다. Next.js 15 보안 지원은 2027-01-31까지이므로 호스팅 지원 상태에 맞춰 후속 업그레이드가 필요합니다.
- 간접 의존성 보안 패치를 위해 grpc-js, glob, minimatch, postcss override를 적용했습니다. 상위 라이브러리가 패치 버전을 요구하게 되면 제거 여부를 재검토합니다.

## 검증 범위

`npm test`는 HTML 정화, 비공개 API와 SSR 조회, 수정 필드 보존, 관리자 권한, 날짜, 실제 파일 형식과 스트림 크기 제한을 검사합니다. Firestore/S3는 테스트 대역을 사용하므로 운영 DB/버킷에 쓰지 않습니다. 테스트에 Node VM Modules 실험 플래그를 사용합니다.

실제 Firebase 키 없이 빌드를 검증할 수 있습니다. 이 경우 목록/사이트맵 데이터 조회 오류 로그는 예상되며 실제 Firebase 연결 성공을 의미하지 않습니다. GitHub OAuth와 S3 업로드를 포함한 운영 연결 검증은 스테이징에서 별도로 해야 합니다.

## 4. DB 커서 페이지네이션

- 홈/목록 API는 Firestore에서 최대 20개(+ 다음 페이지 판단 1개)만 읽습니다. 서버가 허용하는 최대 페이지 크기는 50개입니다.
- `sortAt DESC, 문서 ID DESC`로 동일 날짜에서도 정렬/커서가 일치합니다. 공개/관리자/카테고리별 커서를 혼용하면 400으로 거부합니다.
- 공개 목록은 DB 쿼리부터 `visibility=public` 조건을 사용하고, 반환 직전 기존 공개 플래그도 검사합니다.
- 전역 카테고리 개수와 전체 개수는 집계 문서에서 조회하며 생성/수정/삭제와 같은 트랜잭션에서 갱신합니다. 비공개 개수/카테고리는 공개 응답에 넣지 않습니다.
- 이전 문서 정규화와 인덱스 파일, dry-run/백업을 요구하는 마이그레이션을 추가했습니다. 준비되지 않은 DB는 데이터를 누락시키는 대신 503을 반환합니다.
- 사이트맵만 전체 공개 글을 페이지 단위로 순회합니다. 편집으로 정렬 위치가 바뀌면 다음 새로고침에서 새 순서가 반영되며, 클라이언트는 중복 ID를 제거합니다.

## 5. 비공개 첨부와 운영 권한

- 새 업로드는 공개 접근이 차단된 기존 버킷을 재사용합니다. S3 URL 대신 인증하는 미디어 API의 ID를 저장합니다.
- 업로드 소유자, 대상 글/포트폴리오 연결, 공개 여부를 검증합니다. 연결과 공개 전환은 DB 트랜잭션으로 함께 반영합니다. 다른 글에서 쓰는 파일이나 삭제 중인 파일을 재사용할 수 없습니다.
- 미디어 API는 이미지뿐 아니라 동영상 Range/HEAD 요청도 지원하고 캐시하지 않습니다. 관리자 세션은 HttpOnly 쿠키로 전달하고 동일 출처 검사로 생성합니다.
- Firebase 키는 기존 Amplify 서버 환경변수로 읽습니다. 허용된 변수만 서버용 `.env.production`에 전달하고, 빌드 인라인 주입이나 로그 출력을 하지 않습니다. 별도 비밀 저장 서비스 의존성은 제거했습니다.
- 기존 버킷의 최소 IAM 권한 예시, Firestore deny-all 규칙, 기존 객체를 복사하지 않는 첨부 등록 도구, 버킷 공개 차단 도구, 읽기 전용 운영 확인 도구를 추가했습니다. 새 버킷/역할을 만드는 CloudFormation은 제거했습니다.

## 6. 작성 화면 분리

- CodeMirror 생성/정리/텍스트 삽입/제목·목록 조작을 `useMarkdownEditor`로 분리했습니다.
- 미리보기 파일 변환/검증/업로드를 `usePostMedia`로 분리했습니다. 저장 재시도에서 이미 업로드한 파일을 재사용하고, 취소된 미연결 업로드를 정리합니다.
- 표 편집기는 별도 컴포넌트이며 미리보기/상세의 HTML 정화 방식은 공유합니다.

## 운영에 적용해야 효력이 생기는 항목

코드/설정 파일을 준비한 것과 실제 운영 적용은 구분합니다. [적용 순서](AMPLIFY_ENV.md)에 따라 기존 환경변수 전달, 인덱스/규칙, 기존 객체 참조 마이그레이션과 기존 버킷 공개 차단을 적용해야 합니다. 이전 버킷의 공개 접근을 차단하기 전까지 과거 S3 주소는 여전히 접근 가능할 수 있습니다.

이미 손상된 작성일/통계는 신뢰할 수 있는 백업 없이 복원하지 않습니다. 실제 OAuth 로그인·IAM·S3 연결과 규칙 배포 상태는 스테이징에서 검증해야 하며 로컬 테스트 대역의 통과만으로 운영 성공을 주장하지 않습니다.
